# 需求文档写作规范

所有产出文档适用。目标是让文档读起来像一位有经验的业务分析师写的交付物，而不是模型生成的填充物。

## 1. 判断标准

一句话如果删掉之后，读者对系统的理解没有任何损失，这句话就不该存在。写完每段回头问一遍：这段给出了什么此前不知道的信息？答不上来就删。

## 2. 禁用词表

下列词出现即视为缺陷。分两栏的原因：中文没有词边界，校验脚本只能做子串匹配，短词作为子串会大面积误伤正常表述。**能被脚本可靠捕获的进 2.1，会误伤的进 2.2 交给人**。两栏的词不重复，`scripts/self_check.py` 的 S06 核对 2.1 与脚本常量逐字一致。

### 2.1 脚本扫描（C08 会报）

**空洞形容词**：高效、便捷、友好、强大、灵活、丰富、完善、全面、优质、卓越、极致、丝滑、无缝

**营销黑话**：赋能、抓手、闭环、打通、生态化、中台化、一站式、全方位、深度融合、有效提升、显著改善

**过渡废话**：值得注意的是、需要强调的是、众所周知、不难看出、综上所述、总而言之、总的来说、由此可见、在这个基础上、与此同时

**万能开场**：本模块旨在、本文档旨在、为了更好地、随着业务的发展、在当今、通过合理的设计

**模糊量词**：一定程度上、相对较、较为、通常情况下、一般来说、大量地

**需求异味**：尽可能、尽量、令人满意、足够好

需求异味让需求不可测——「尽可能快」没有阈值、「令人满意」无法判定通过与否，一律改写为可量化准则。

### 2.2 人工自查（脚本不扫）

同样禁用，但脚本不扫——子串匹配会误伤。写完自查这一栏。

| 词 | 不扫的原因 | 脚本改扫的替代形式 |
|----|------------|--------------------|
| 大量 | 「大量数据」「大量并发」是合法的领域表述 | 「大量地」 |
| 少量 | 「少量灰度」在版本计划里是正常说法 | —— |
| 若干 | 「若干子模块」在关系类型定义里必须用 | —— |
| 比较 | 「比较两个方案」是动词，与模糊量词无关 | —— |
| 可能会 | 「可能会失败」在异常流里是必要的不确定表达 | —— |
| 生态 | 「生态伙伴」可能是真实业务名词 | 「生态化」 |
| 链路 | 作名词指调用链路时合法，只有作形容词时才是黑话 | —— |

模糊量词的替换方式是给数字。写不出数字就标 `[待确认: 具体阈值]`，不要用模糊词掩盖。

新增禁用词时先判断归哪一栏：拿这个词在已有文档里搜一遍，只要存在一个合法用法就进 2.2，或者换一个更长、不会误伤的变体进 2.1（「大量」→「大量地」就是这么来的）。

## 3. 禁用句式

| 禁用 | 原因 | 改成 |
|------|------|------|
| 首先…其次…最后… | 编号列表已经表达顺序 | 直接用有序列表 |
| 不仅…而且… | 两件事就分两条写 | 拆成两条 |
| A 的同时，也 B | 同上 | 拆成两条 |
| …等 | 掩盖清单不完整 | 列全，或写「以下 N 项」 |
| 通过 X 来实现 Y | 绕 | X 实现 Y |
| 对 X 进行 Y | 动词名词化冗余 | 直接用动词：Y X |
| 系统会自动… | 主语含糊 | 写明是哪个模块 |
| 用户可以方便地… | 「方便地」无信息 | 写清操作路径和结果 |

**结尾总结段一律不写**。需求文档不是议论文，模块文档写完变更记录就结束。

## 4. 结构偏好

优先级：表格 > 有序列表 > 无序列表 > 段落。

- 凡是「多个对象 × 多个属性」的信息，一律用表格。业务规则、字段定义、异常处理、关系视图都属于这类。
- 流程用有序列表，每步写「角色 + 动作 + 产出」，一步一行。
- 段落只用于交代背景和边界说明，连续段落不超过 3 段。
- 不要三段式强迫症。该写两点写两点，该写七点写七点，不为了对称凑数。
- 不用 emoji。不用「✅」「⚠️」这类符号做正文标记，表格里用「是/否」「必填/选填」。

## 5. 强制程度用词

采用 RFC 2119 风格，全文一致：

| 用词 | 含义 |
|------|------|
| 必须 / 不得 | 硬性要求，不满足即不通过验收 |
| 应当 / 不应 | 推荐要求，偏离需在文档中说明理由 |
| 可以 | 可选，实现方自行决定 |

不要用「需要」「要求」「建议」这类强度不明的词。

## 6. 具体化要求

每条需求都要能回答：谁、在什么条件下、做什么、得到什么结果、失败了怎样。

反例与改写：

> ❌ 系统应支持高效的订单查询功能，方便用户快速找到所需订单。

> ✅ 买家在订单列表页按订单号、商品名称、下单时间范围检索历史订单。检索结果按下单时间倒序分页返回，每页 20 条。检索范围限最近 24 个月，超出范围的查询返回空列表并提示「仅支持查询近两年订单」。响应时间要求见 `NFR-0002`。

改写后多出的信息：检索入口、检索维度、排序规则、分页大小、时间边界、越界表现、性能引用。这些才是需求。

## 7. 不确定性的表达

推断出来的内容不许写成确定事实。三种标记：

- `[待确认: 问题描述]` —— 需要干系人回答才能定稿
- `[推测: 依据]` —— 基于常识补的，标明推断依据
- `[新增术语提案]` —— 术语表里没有的新名词

宁可满篇标记，不许编造细节填空。**编造一个看似合理的字段名或阈值，比留空的代价大得多**——留空会被追问，编造会被当成事实实现。

## 8. 交叉引用

- 引用其他模块：写全 `[MOD-0003 库存扣减](../modules/MOD-0003-库存扣减.md)`，不写「如前所述」「参见相关模块」。
- 引用 NFR：写 `NFR-0002`，不复述指标数值。
- 引用术语：直接用术语表标准名，不加解释、不加括号注释。需要解释说明术语表定义不清，去改术语表。

## 9. 自查清单

提交每份文档前逐条过：

1. 全文搜一遍禁用词表，命中即改。
2. 每个形容词问一次：能换成数字吗？
3. 每个「系统」做主语的句子，换成具体模块 ID。
4. 有没有一段话只是把标题换个说法重复一遍？删。
5. 有没有段落超过 5 行还没给出一条可验证的信息？改成表格。
6. 术语是否全部来自术语表，有无同义替换。
7. 所有不确定项是否都带标记。

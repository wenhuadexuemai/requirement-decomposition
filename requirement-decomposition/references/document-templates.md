# 产物填写指引

空白模板在 `assets/templates/`，直接复制后填写。本文说明每个字段的填写标准和常见错误，不重复模板本身。

## 产物清单

| 产物 | 数量 | 文件路径 | 模板 |
|------|------|----------|------|
| 综述 | 1 | `00-综述.md` | `assets/templates/overview.md` |
| 术语表 | 1 | `01-术语表.md` | `assets/templates/glossary.md` |
| 需求跟踪矩阵 | 1 | `02-需求跟踪矩阵.md` | `assets/templates/traceability.md` |
| 版本计划 | 1 | `03-版本计划.md` | `assets/templates/release-plan.md` |
| 版本快照 | 1 | `04-版本快照.md` | `assets/templates/version-snapshot.md` |
| 功能模块文档 | 每模块 1 份 | `modules/MOD-NNNN-名称.md` | `assets/templates/module.md` |
| 端到端场景切片 | 3~5 份 | `scenarios/UC-NNNN-名称.md` | `assets/templates/scenario.md` |
| 决策记录 | 每个争议决策 1 份 | `decisions/ADR-NNNN-标题.md` | `assets/templates/adr.md` |

目录结构：

```
需求文档/
├── 00-综述.md
├── 01-术语表.md
├── 02-需求跟踪矩阵.md
├── 03-版本计划.md
├── 04-版本快照.md
├── modules/
│   └── MOD-0001-xxx.md
├── scenarios/
│   └── UC-0001-xxx.md
└── decisions/
    └── ADR-0001-xxx.md
```

## 一、综述

综述是整个文档网络的入口和索引，九个必含项缺一不可。

### 1. 系统概述与范围

写背景、目标、**范围外**三块。范围外单独成节，逐条列出本期不做的事及原因——这一节的价值高于目标，它是后续争议的裁决依据。

附 Mermaid 上下文图（C4 Context 层级），画系统与外部角色、外部系统的交互，不画内部模块。

角色权限用表格：角色名、职责描述、可触达模块 ID 列表。

### 2. 全局 NFR

每条分配 `NFR-NNNN`，字段为：ID、类别、指标描述、量化阈值、测量方式、违反后果。

**指标必须可测**。「响应快」不是 NFR，「列表接口 P95 响应时间 ≤ 800ms，压测并发 200」才是。写不出阈值的先标 `[待确认]`，不要用形容词凑数。

类别覆盖：性能、可用性、安全、合规、可维护性、兼容性、可观测性。用不到的类别写「本期不涉及」并说明理由，不要省略。

### 3. 术语表

见下方独立章节。综述中放链接与摘要，不复制全表。

### 4. Mermaid 功能结构图

三张图，缺一不可：

- **分层包含图**（`graph TD` + `subgraph`）：模块归属的业务域层级。
- **依赖关系图**（`graph LR`）：模块间依赖，边上标关系类型，强依赖实线 `-->`、弱依赖虚线 `-.->`。
- **数据流图**（`flowchart LR`）：核心数据实体在模块间的流转方向，边上标数据实体名。

节点文本一律写成 `MOD-0001<br/>订单创建`，带 ID。C14 会检查图内的真实 `MOD-NNNN` 是否在模块索引登记，引用未登记的模块会报 WARN；泛指写 `MOD-NNNN` 不触发。

### 5. 模块索引目录

表格字段：模块 ID、名称、一句话目标、文档链接、关系概述、引入版本、状态。

状态取值与转移条件见 `decomposition-rules.md` 第 8 节。本列是视图，权威源是各模块文档头部的状态行。

### 6. 关系矩阵

字段：源模块 ID、目标模块 ID、关系类型、关系描述、置信度、依赖强度、降级策略。

关系类型只能取 `references/decomposition-rules.md` 第 5 节的九种。每条关系在双方文档中都要出现，方向互补。降级策略仅弱依赖必填，强依赖填「不可降级，失败表现见模块文档」。

矩阵随任何模块变更同步更新，这是硬性要求。

### 7. 需求跟踪矩阵主表

见下方独立章节。综述中放链接，不复制全表。

### 8. 全局跨模块规则

跨越两个以上模块的通用规则集中在此，例如统一的时间格式、金额精度与舍入、幂等键约定、状态机通用迁移规则、审计日志字段。

每条规则给 ID（沿用 `NFR-NNNN` 或另起 `RULE-NNNN`），模块文档引用不复述。

### 9. 移交事项

本技能只写需求，不写技术方案。碰到技术选型、部署拓扑、接口协议、库表设计这类问题，把需求侧的约束写清，实现方式列进本表移交出去。

字段：事项、为什么不在本网络内定、移交给谁、相关模块、未决时的影响。

判据是**需求已定、实现方式未定**。「订单号全局唯一且不可推测」是需求，写进数据需求；「用雪花算法还是 UUID」是实现，进本表。

反过来，需求本身没定的事不进这里——那是 `[待确认]` 标记或访谈的未决项，两者不要混。混了以后没人能从这张表分清「等别人决定」和「我们还没想清楚」。

本节的价值在交付之后：半年后有人问「当初接口协议是谁定的」，只在对话里说过的移交没有痕迹，写进综述的能查。

## 二、功能模块文档

首行固定引导语：

> 本文档需结合《[综述](../00-综述.md)》与《[术语表](../01-术语表.md)》阅读。文中术语均为术语表标准名。

必含项与填写要点：

| 章节 | 要点 |
|------|------|
| 模块 ID / 名称 | 与综述索引完全一致 |
| 目标与范围 | 一句话目标 + 范围外清单 |
| 关系本地视图 | 从综述关系矩阵摘录与本模块相关的行，**摘录不改写**，加一列「本模块视角说明」 |
| 前置 / 后置条件 | 前置写进入本模块前系统必须满足的状态；后置写正常结束后的状态变化，含数据落库结果 |
| 主要流程 | 分基本流、备选流、异常流。每步写「序号 + 角色 + 动作 + 产出」。异常流覆盖每个外部依赖的失败分支 |
| 业务规则清单 | 表格：规则 ID（`MOD-NNNN-REQ-NNNN`）、规则描述、触发条件、优先级、来源 |
| 界面引用 | `UI-NNNN` + 原型链接 + 该界面涉及的交互约束，不描述视觉样式 |
| 数据需求 | 实体名（必须是术语表标准名）、属性、类型、必填性、取值约束、写主标注 |
| **全局 NFR 适用性声明** | 强制，见下 |
| 特有 NFR | 仅本模块独有的指标，全局已有的不重复 |
| 验收标准 | 每条对应跟踪矩阵中的验收 ID，写成可执行的 Given-When-Then |
| 参与场景 | 本模块出现在哪些 `UC-NNNN` 中，带链接 |
| 变更记录 | 日期、变更人、变更内容、影响的其他文档 ID |

### NFR 适用性声明（强制）

逐条应答综述中的**每一个** `NFR-NNNN`，三选一：

| 结论 | 要求 |
|------|------|
| 完全适用 | 直接引用，不复述阈值 |
| 部分适用 | 说明适用的部分和不适用的部分，分别给理由 |
| 不适用 | 必须给理由，理由不得是「本模块不涉及」这类同义反复 |

**禁止留白，禁止只写「适用」两字**。NFR 数量与声明条数不一致时校验脚本报错。

## 三、端到端场景切片

覆盖 3~5 条核心业务旅程。作用有两个：反向验证模块拆分是否合理（跑不通就是拆错了），以及作为集成测试输入。

必含项：

- 场景 ID / 名称 / 业务价值
- 参与角色
- 模块顺序流：Mermaid 泳道图（`sequenceDiagram`），参与者为角色和模块 ID
- 步骤详解表：序号、触发模块、输入、处理、输出、流向下一模块
- 数据传递：跨模块传的数据实体和关键字段，标明在哪一步产生、哪一步消费
- 异常路径：至少覆盖 2 条真实可能的失败路径，写清补偿或回退动作，关联模块的异常流

场景中引用的模块流程步骤必须与模块文档的步骤编号对得上。对不上说明两边不一致，改到一致为止。

## 四、术语表

字段：术语 ID、标准名、定义、**禁用同义词**、**豁免上下文**、是否为数据实体、权威来源、首次出现文档。

禁用同义词一列是核心——把实际业务中会混用的说法全部列出来，校验脚本据此扫描全文报警。

数据实体类术语额外标注属性清单和写主模块。

## 五、需求跟踪矩阵主表

一行一条需求，字段：需求 ID、所属模块 ID、关联场景 ID、需求简述、优先级、需求来源、架构/UI 引用、验收标准 ID、目标版本、特性开关名。

- 优先级用 MoSCoW（Must / Should / Could / Won't）。
- 需求来源写到可追溯的粒度：原始文档名 + 章节号，或会议名 + 日期 + 提出人。写「业务方提出」等于没写。
- 特性开关名在需要灰度的需求上必填。

矩阵是双向追溯的枢纽：从需求能找到模块和验收，从模块能反查需求覆盖。任何模块文档里的 `MOD-NNNN-REQ-NNNN` 都必须在矩阵中有对应行。

## 六、决策记录（ADR）

需求文档写「是什么」，决策记录写「为什么不是别的」。被否决的方案是最容易丢失的信息——半年后有人问「当初为什么不用 X」，没有 ADR 就只能重新吵一遍。

**什么时候写**：一个决策满足下列任一条就该建 ADR。

| 触发条件 | 例子 |
|----------|------|
| 有过真实争议，两个以上方案被认真考虑过 | 库存是预占还是下单时扣减 |
| 决策会约束后续多个模块 | 全局幂等键约定、时间格式 |
| 违反了某条既有原则，需要留档例外 | 「一份数据一个写主」的破例 |
| 决策依赖的前提可能变化 | 「V1 不引入向量检索，量级到十万级再评估」 |

反过来，没有争议的事实（「订单号用 UUID」）不需要 ADR，写进模块文档的数据需求即可。**ADR 不是需求的复制品**。

必含项与填写要点：

| 章节 | 要点 |
|------|------|
| 属性表 | 状态、日期、决策者（拍板人或评审会议名 + 日期）、影响范围 |
| 背景 | 什么问题逼出这个决策。写清约束和不决策的后果 |
| 可选方案 | **至少两个**。只有一个方案说明在记录既成事实，不是决策 |
| 决策 | 选了哪个、具体怎么做，写到能据此实现的粒度 |
| 理由 | 逐条对应「为什么不是其他方案」，不写空泛好处 |
| 后果 | 生效后系统变成什么样，好的坏的都写 |
| 副作用 | 被否方案不会有、本方案会有的额外成本。写不出通常说明评估不充分 |
| 不做什么 | 明确排除的做法及原因，挡住后续反复讨论 |
| 关联 | 影响的模块（Markdown 链接）、相关 NFR、相关 ADR |

状态取值：`提议` / `已采纳` / `已废弃` / `被取代`。被取代时写明取代它的 ADR 编号。

**决策被推翻时追加，不覆写**。后续评审改了决策，在变更记录追加一行并在正文补「修订」小节，保留原判断——被推翻的判断本身就是决策依据的一部分，覆写掉就等于把「我们试过这条路」的信息删了。

ADR 与模块文档的引用是双向的：ADR 在「关联」节点名模块，模块在相关规则处引用 `ADR-NNNN`。`impact_analysis.py` 依此双向传播——改了决策会列出它点名的模块，改了模块会列出点名它的决策。

## 七、版本计划

字段：版本号、目标、包含模块、包含需求、前置版本、发布条件。

跨版本降级策略针对这种情况：模块 A 在 V1 上线，它弱依赖的模块 B 排在 V2。V1 期间 A 如何运行，必须在此写清。缺这一项的版本计划不算完成。

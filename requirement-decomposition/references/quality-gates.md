# 质量护栏

护栏由八个脚本承载，都在 `scripts/` 下，只依赖 Python 标准库。

护栏分三层，别混：**六个管技能产出的文档**，`run_routing_evals.py` 管技能包自身的触发用例，`self_check.py` 管技能包自己。写需求文档时跑第一层，改这个技能包时跑后两个。

| 脚本 | 作用 | 典型时机 |
|------|------|----------|
| `validate_interview.py` | 骨架访谈契约校验 | 第 2 轮每个提问回合后 |
| `scaffold_docs.py` | 按骨架 JSON 展开整套文档目录 | 第 2 轮获批后 |
| `validate_requirements.py` | 十六项一致性检查 | 每轮结束、提交前、CI |
| `impact_analysis.py` | 变更影响推导与同步性检查 | 变更后、合并前 |
| `run_routing_evals.py` | 触发边界用例结构校验 | 改动 SKILL.md 的 description 后 |
| `manual_review_checklist.py` | 列出脚本管不到、需人工过的复核项 | 定稿前人工复核 |
| `build_view.py` | 按视图配方把多个模块的指定章节拼成聚合视图 | 人读集中评审时 |
| `self_check.py` | 技能包自身的内部契约自检 | 改动本技能包任何文件后 |

八个脚本都不依赖外部网络、托管平台或第三方库。`impact_analysis.py` 默认从 git 取变更集，但 git 只是取变更集的一种方式，`--changed-files` 可绕开。

## 〇、访谈契约

```bash
python3 scripts/validate_interview.py --print-example                    # 最小合法状态样例
python3 scripts/validate_interview.py --state interview-state.json --transcript transcript.json
python3 scripts/validate_interview.py --state s.json --transcript t.json --skeleton skeleton.json
```

退出码：0 通过，1 契约错误，2 用法或读取错误。失败即拒绝（fail closed）。

检查的契约项：

| 类别 | 内容 |
|------|------|
| 证据 | 第一个提问之前必须有 `evidence_read` 事件；每条证据需路径、SHA-256、结论 |
| 提问 | 一个回合恰好一句问句；必带推荐答案与理由；必须说明已知证据 |
| 应答 | `answer` 必须对应在先的提问，且已答问题都要进决策记录 |
| 门禁 | 八项全真才可进 `ready-for-skeleton` 及之后；阻塞未决项未清不得过门禁 |
| 批准 | 草稿之后必须有显式 `approval`；沉默、答非所问都不算批准 |
| 硬停止 | 批准前 `expansion_allowed` 必须为假；批准前出现展开或实现动作即报错 |
| 恢复 | `resume` 记录的状态摘要须与文件实际内容相符，且接续存下的 `next_question_id` |

状态摘要按规范文本字节算 SHA-256：严格 UTF-8 解码，CRLF 与孤立 CR 归一为 LF，再编回 UTF-8。只归一换行，因此 Windows 与 Unix 上摘要一致，而除换行外的任何改动都能被检出。

## 一、脚手架

```bash
python3 scripts/scaffold_docs.py --print-schema          # 查看骨架 JSON 结构
python3 scripts/scaffold_docs.py skeleton.json -o ./需求文档
python3 scripts/scaffold_docs.py skeleton.json -o ./需求文档 --force   # 覆盖已存在文件
```

骨架 JSON 含 `project`、`nfrs`、`modules`、`scenarios`、`relations` 五个必需字段，以及可选的 `decisions`（决策记录）。脚本会：

- 生成综述并把模块索引表、NFR 表、关系矩阵按骨架填好；
- 为每个模块生成文档，**NFR 适用性声明表按全局 NFR 逐条预填行**，从源头杜绝漏项；
- 为每个模块在跟踪矩阵预置一行 `MOD-NNNN-REQ-0001`；
- 为 `decisions` 中的每一项生成 `decisions/ADR-NNNN-标题.md`（省略该字段则不生成）；
- 生成 `04-版本快照.md`（空壳，评审定版后用 `--snapshot` 追加基线记录）；
- 默认不覆盖已存在文件，避免误伤已填内容。

新增模块时，把新模块追加进骨架 JSON 重跑即可，已有文档不受影响。

## 二、一致性校验

```bash
python3 scripts/validate_requirements.py ./需求文档
python3 scripts/validate_requirements.py ./需求文档 --only C04,C05   # 只跑指定项
python3 scripts/validate_requirements.py ./需求文档 --format json    # 机器可读
python3 scripts/validate_requirements.py ./需求文档 --strict         # 警告也算失败
```

退出码：0 通过，1 存在 ERROR，2 用法错误。

### 检查项与修复指引

| 编号 | 检查项 | 触发条件 | 修复方向 |
|------|--------|----------|----------|
| C01 | 文档结构与必需文件 | 缺产物、模块文档与索引不匹配、模块 ID 重复、场景数不在 3~5 之间 | 补文件或补索引行，两侧对齐 |
| C02 | ID 定义与引用完整性 | 引用了未在索引/NFR 表/场景文件/术语表/决策记录中定义的 ID；ID 某段序号不足四位；同一 UI ID 对应不同界面名 | 要么补定义，要么改引用，不留悬空 ID |
| C03 | 相对链接可达性 | 链接指向不存在的文件；提到其他模块 ID 却没做成链接 | 修路径；跨文档引用一律写成 Markdown 链接 |
| C04 | NFR 全覆盖声明 | 模块缺 NFR 声明表、漏条目、结论非法、理由是同义反复 | 逐条补齐，「不涉及」不算理由 |
| C05 | 关系矩阵合法性与对称性 | 关系类型/置信度越界、弱依赖缺降级策略、双方本地视图不对称、依赖/顺序成环 | 按词表改类型，补策略，双向登记，打破环路 |
| C06 | 需求跟踪矩阵完整性 | 需求 ID 格式错、模块不存在、前缀不匹配、缺优先级/来源/验收、模块内 REQ 未入表、验收标准悬空或孤儿；附覆盖率统计输出（INFO） | 补矩阵行或修 ID，验收双向对齐 |
| C07 | 术语一致性 | 正文出现术语表禁用同义词列中的说法（标准名的各语言形式均合法，不报） | 换成标准名的相应形式；确属无关表述则登记豁免；确需新词则走新增术语提案 |
| C08 | 写作规范 | 命中禁用词表（空洞形容词、营销黑话、过渡废话、模糊量词、需求异味等） | 见 `writing-style.md`，改成可验证的具体表述 |
| C09 | 占位符与未决项 | 残留 TODO / TBD / xxx；统计已标记的未决项数量 | 未定内容一律改用 `[待确认: 描述]` 形式 |
| C10 | 表格结构与豁免标记卫生 | 豁免标记含 `\|` 或落在分隔行上破坏表格；标记点名的词本行不存在或不在禁用词列中；豁免上下文填的搭配不含该行任一禁用同义词；禁用同义词列出现标准名的某形式（等于禁用自己的标准名）；表格行列数与表头不符（单元格里的 \| 被当列分隔符，或末尾漏 \|） | 多个词用顿号分隔；撤掉空转的标记；标准名各形式都合法，从禁用同义词列去掉 |
| C11 | 文档版本一致性 | 版本不是三段号（V1、V1.0、v0.1）；缺「文档版本」行；头部版本与变更记录最新条目对不上；版本序列跳号或倒退；修订标记引用了变更记录里没有的版本 | 统一写成 `V1.0.0`；改正文同步加变更记录行 |
| C12 | 模块体量合理性 | 业务规则表真实行数过少（≤2，存在感偏低，考虑并入相邻模块）或过多（>30，考虑拆子模块）；规则表为空或全占位时不报 | 合并或拆分由人定，机器只报信号 |
| C13 | 数据写主唯一性 | 同一 (实体,属性) 在多个模块被标为写主；术语表数据实体表的写主与模块文档的写主不一致 | 按实体名精确匹配，异形同义不报（漏报但不误报）；确认是冲突还是异形，两处登记对齐 |
| C14 | Mermaid 图内模块 ID | Mermaid 图引用了未在模块索引里登记的模块 | 补模块或在图中改用已登记的 ID；泛指写 `MOD-NNNN` 不触发 |
| C15 | 文档状态一致性 | 状态取值不在词表内、为空；模块索引表的状态列与模块文档头部不一致；标了「已冻结」却不在任何一次基线里，或当前版本与基线记录的版本对不上（均 WARN）；缺「状态」行（WARN） | 取值见 `decomposition-rules.md` 第 8 节；两处一起改，权威源是模块文档；已冻结要先进基线，进基线后又改过就退回草稿或补打快照 |
| C16 | 终态文档引用完整性 | ADR 标「被取代」但正文没写取代者编号（WARN）；取代者没声明取代关系（WARN）；循环取代（ERROR）；已废弃模块仍出现在关系矩阵的源/目标中（WARN） | 被取代是关系性状态，不写编号就是话只说了一半；关系矩阵是活跃依赖声明，废弃模块不该还在里面。只查结构化引用（ADR 正文 + 关系矩阵列），不查自由文本 |

C04 对「结论列填的是 `[待确认: ...]`」判为 WARN 而非 ERROR——这是承认的过程态。**定稿必须清零 WARN**，用 `--strict` 卡这一关。

### C07 的豁免机制

中文没有词边界，禁用同义词是子串匹配，同形异义必然存在——「回退」是「撤销」的禁用同义词，但「路由失败回退加载核心工具」里的「回退」与撤销无关。这类误报判 ERROR 会逼人关掉整项检查，所以 **C07 命中一律判 WARN**，并提供两级豁免：

| 方式 | 作用域 | 用法 |
|------|--------|------|
| 术语表「豁免上下文」列 | 全库 | 填该行禁用同义词的正常搭配，顿号分隔，如 `回退加载、失败回退`。搭配可含空格（如复合字段名 `Matter 摘要`）；空格属于短语内部，不是搭配之间的分隔符 |
| 行内 `<!-- term-ok -->` | 单行 | `<!-- term-ok: 回退 -->` 只豁免该词；不写词则豁免整行 |

判断标准：某个搭配在文档里反复出现且确与术语无关，进「豁免上下文」列；只在一两处出现的例外，用行内标记。**豁免的是搭配不是词本身**——「回退加载」被豁免后，「执行回退」仍会报警。

豁免按**出现位置**生效，不是整行生效：同一行里「路由失败回退加载」被掩护，「用户执行回退」仍会报出来。一个合法搭配不会掩护掉同行的真实违规。

不参与扫描的内容：代码块、行内代码（`` `回退` `` 是在提这个词而非用它）、表格的表头行与分隔行（表头由模板定死，且校验器靠表头关键词定位表格，不能既要求它不动又对它报违规）、豁免标记自身。行号按原文计算。

标准名的各语言形式也不参与扫描：标准名写 `Order / 订单` 时，中文文档用「订单」、英文语境用「Order」都合法，只有禁用同义词列登记的说法才报 C07。

### 豁免标记写在表格里要当心

C07 的违规多数出现在表格中，而 **HTML 注释里的 `|` 会被 Markdown 表格当成列分隔符**。写成 `<!-- term-ok: 回退|撤回 -->` 会把本行的列整体切错位，后果是别的检查项报出一堆看不懂的错——关系类型变成「依赖 <!-- term-ok: 回退」、置信度里装着关系描述——而真实原因是那个注释。C10 直接检出这种写法。

| 写法 | 结果 |
|------|------|
| `<!-- term-ok: 回退、撤回 -->` | 正确，顿号分隔 |
| `<!-- term-ok: 回退\|撤回 -->` | C10 报 ERROR，列会错位 |
| 放在表格分隔行上 | C10 报 ERROR，整张表解析不出来 |
| 放在表格行尾（多一列） | 可用，多出的单元格被丢弃 |

标记点名的词若本行不存在，或不在术语表禁用同义词列中，C10 判 WARN：这类空转标记会掩护以后写进这一行的真实违规。

### 术语表「豁免上下文」列填「——」不等于没填

这一列的空位标记（`——`、`无`、`-`、`N/A`）不会被当成搭配。曾经会：模板预填的 `——` 被收进豁免集合后，全库每一行只要含破折号就整行豁免，C07 静默失效——报表不会显示「跳过」，只显示「0 警告」。

### 三种「版本」不是一回事

版本号写法漂移（同一批文档里 V1、V1.0、v0.1、不写四种并存）的根源不是笔误，是三个不同语义共用了「版本」这个词。**只有第一种由本技能定义格式**，另两种沿用产品既有约定，不强加三段号。

| 语义 | 字段名 | 格式 | 谁定 |
|------|--------|------|------|
| 文档修订 | `文档版本` | `V<主>.<次>.<修订>` | 本技能，C11 校验 |
| 产品发布 | `目标版本` | 产品自己的约定 | 产品，本技能不管 |
| 模块引入 | `引入版本` | 引用产品发布版本 | 产品，只记录不校验 |

把模块的「引入版本」也改成三段号是错的——它记的是「这个模块从哪个产品版本开始存在」，写成 `V1.0.0` 反而污染了产品版本语义。

### 文档版本怎么进位

判据是**读者是否需要重读**，不是改了多少字。文档的消费者是评审人和实现方，他们关心的是「我上次读的还算不算数」。

| 位 | 什么时候进位 | 例子 |
|----|--------------|------|
| 主版本号 | 需求范围增删或边界改动，读者需重读全文 | 模块拆分、职责重划、范围外条目移进范围内 |
| 次版本号 | 新增章节内容或结论变化，局部重读即可 | 补一条业务规则、NFR 阈值调整、新增异常流 |
| 修订号 | 措辞、补充说明、修正笔误，不影响结论 | 改错别字、补充示例、调整表格顺序 |

一次只进一位，进位时低位归零。骨架展开时全部 `V1.0.0`。

改了正文必须在变更记录里加一行，头部的「文档版本」与变更记录最新一条必须相等——C11 卡这一条。对不上说明改了正文没记录，或记了没更新头部。

### 后期改动前阶段内容的三种展现

需求文档的读者会跨版本引用：第 3 轮写的模块文档被第 5 轮的场景引用了确切步骤编号。第 6 轮改需求时直接删掉那一步，场景的引用就悬空了——而 C02/C03 只查 ID 和链接，查不出「步骤 4 曾经存在现在没了」。

| 形式 | 用在 | 写法 |
|------|------|------|
| 变更记录行 | 所有改动 | 变更记录表加一行，写清版本、改了什么、影响哪些文档 |
| 行内修订标记 | 结论变了且旧结论已被引用 | `<!-- rev: V1.1.0 原为「保留 7 天」，因合规要求调整 -->` |
| 废止标注 | 整节作废 | 保留原文加删除线，标 `[V1.2.0 废止: 理由]`，不直接删 |

**不直接删是为了让引用方看到发生了什么**。修订标记与废止标注引用的版本必须在本文档的变更记录里存在，C11 判 WARN。

行内修订标记沿用 HTML 注释，与 `<!-- term-ok -->` 同族——**写在表格行里时不能含 `|`**，这条由 C10 统一拦截。

### 版本快照

评审定版时锁定基线，回溯「上次评审时全库长什么样」：

```bash
python3 scripts/validate_requirements.py ./需求文档 --snapshot 2026-08-09 >> ./需求文档/04-版本快照.md
```

脚本读取全库实际版本与状态生成，不手工维护——快照的价值全在「与实际一致」，手抄一份必然漂移，那时它记录的就不再是基线，而是某人上次记得更新的时刻。

输出三列：文档、版本、状态。缺状态列的基线表记不下「是否通过评审」这一半信息，那它记录的就只是某次脚本运行。

非「已评审」的文档会在 **stderr** 列出（标准输出要被 `>>` 追加进文档，提示混进去就成了基线正文），配 `--strict` 时退出 1。ADR 走决策处置词表，不进门禁清单；版本快照自身不参与生命周期，也不进。

基线落定后把进了基线的文档转「已冻结」。脚本不回写文档——这个包除 `scaffold_docs.py` 外没有回写源文档的脚本（`build_view.py -o` 生成新聚合视图文件，不改源文档，但输出勿指向被扫描的文档目录），破这个约定的代价大于省下的手工。改完跑 `--only C15` 验证，标了已冻结却不在任何基线里会被反向揪出来。

**C15 比对的是版本不是文件名。** 只比名字的话，「进过基线之后又改正文、升了版本、状态没退」这一手完全看不出来——文档名还在基线里，检查照过。基线记录的是某一版的内容，所以已冻结文档的当前版本必须能在基线记录里找到，找不到就是冻结的那一版已经不是现在这一版。

兼容两种情形不报：1.3.0 之前生成的两列基线表（没有版本或填的是空位标记）只判「进过基线」，版本无从比对；基线与文档头部的版本大小写不同（C11 允许 `V1.0.0` 与 `v1.0.0` 两种写法）统一按大写比对。

### 文档状态

四个取值、转移条件、跃迁要同时改的四处，都在 `decomposition-rules.md` 第 8 节，那里是人读版权威源。这里只记三条口径：

| 口径 | 说明 |
|------|------|
| 权威源 | 模块文档头部的状态行。综述模块索引表是视图，两处不一致时 C15 报 ERROR 并给出两个行号 |
| 空白骨架 | 全是「草稿」，C15 零 ERROR 零 WARN。草稿是合法起点，不是缺失 |
| 存量迁移 | 缺「状态」行判 WARN，与 C11 缺版本行同口径，`--strict` 一并卡死 |

回路上唯一的自动强制点在 `impact_analysis.py`：正文改了而状态仍是已评审／已冻结的文档会单独列出。正向路径（草稿→已评审→已冻结）人会记得走，退回草稿是人不想做的动作，只能靠机器盯。

### 分阶段使用

| 阶段 | 命令 | 期望 |
|------|------|------|
| 骨架轮结束 | `--only C01,C05` | 结构与关系合法 |
| 逐模块生成中 | `--only C02,C03,C04,C07` | 单模块自洽，术语当场纠偏 |
| 全局审查轮 | 全量默认 | ERROR 清零 |
| 场景编写后 | `--only C02,C03,C14` | ERROR 清零；场景引用的步骤编号与模块文档是否一致靠人工核（脚本不查步骤号） |
| 定稿 / 合并 | `--strict` | ERROR 与 WARN 均清零 |

**C07 要在写每个模块时就跑，不能留到定稿前**。它是全库唯一会随文档量线性累积的检查项：术语表定了 10 个禁用词、写了 20 份文档，攒到最后就是几十上百条待判定的告警，而每一条都要人读上下文决定「换标准名 / 登记豁免 / 加行内标记」——这个判断没法批量做。逐模块跑的话每次只有三五条，且当场就知道该怎么改。

### ID 序号位数

序号四位起（`MOD-0001`）。写成 `MOD-01` 时ID 正则**根本不匹配**——既不报悬空也不生效，比报错危险。C02 用整串扫描单独检出这种写法并给出正确形式。

逐段检查，不是只看首段：`MOD-0001-REQ-01` 的首段合法、尾段不合法，`AC-0001-01` 同理。五位以上自然合法（`MOD-10000`），不必回头改旧 ID。

## 三、变更影响分析

变更集是这个脚本的输入，取变更集有两条路：

```bash
# 从 git 取（默认，需在仓库内）
python3 scripts/impact_analysis.py --dir ./需求文档 --base origin/main
python3 scripts/impact_analysis.py --dir ./需求文档 --base HEAD~1 --format markdown
python3 scripts/impact_analysis.py --dir ./需求文档 --base origin/main --fail-on-unsynced

# 直接给清单（无 VCS、用 SVN、或变更集来自别处）
python3 scripts/impact_analysis.py --dir ./需求文档 --changed-files changed.txt
git diff --name-only main | python3 scripts/impact_analysis.py --dir ./需求文档 --changed-files -

# 复核确认无需改动的文档，用销项清单抵扣（每行一个路径或 MOD/UC/ADR 的 ID）
python3 scripts/impact_analysis.py --dir ./需求文档 --base origin/main --fail-on-unsynced --cleared cleared.txt
```

邻接传播是粗粒度的：改了模块，它的全部邻接模块都进「受影响」清单，逐份复核后常见「确认无需改动」的结论。这个结论要用 `--cleared` 销项回传给门禁，**不要**靠给这些文档空转版本号+变更记录让门禁闭嘴——空转进位腐蚀 C11 的进位判据（读者是否需要重读）。销项规则：

- 只抵扣「受影响但未同步」；「状态未回退」是更硬的违规，复核结论豁免不了。
- 销项条目在报告里单列并保留原影响原因，CI 日志里可审计，不是静默吞掉。
- 解析不了的条目（错别字、库内没有的 ID）与不在本次受影响清单里的条目（可能沿用了上一轮里程碑的清单）都会在报告里点名。匹配不上等于没销，对应文档仍会报未同步——门禁天然向失败侧倒。
- 销项不跨变更集粘连。里程碑评审时把本轮销项连同结论登记进 `04-版本快照.md` 的「变更复核登记」节，下一轮变更集重新复核、重新登记。

`--changed-files` 接每行一个路径的文本，`-` 表示标准输入。路径相对仓库根或相对文档目录都认。

工作方式：取出变更文档，解析文件名中的模块 ID，依据综述关系矩阵按无向图传播（默认 1 跳），得出受影响模块，再检查这些模块的文档、相关场景文档、综述、跟踪矩阵是否在同一次变更中同步更新。未同步的逐条列出。

固定判定：

- 模块文档变更但综述未动 → 需复核模块索引、关系矩阵、结构图。
- 模块文档变更但跟踪矩阵未动 → 需求条目可能未登记。
- 术语表变更 → 全部文档需复核术语一致性。
- 模块文档变更 → 点名它的决策记录需复核该决策是否仍然成立。
- 决策记录变更 → 它点名的模块文档需复核是否受影响。
- 正文变更但状态仍是已评审／已冻结 → 单独列出「状态未回退」，与「受影响但未同步」分开报（前者是改了没退状态，后者是该改没改）。ADR 与版本快照不参与。

`--depth 2` 可看二跳影响，用于评估结构性改动的波及面。

## 四、触发边界用例

```bash
python3 scripts/run_routing_evals.py                  # 结构校验
python3 scripts/run_routing_evals.py --emit-prompts   # 导出人工复核清单
```

用例在 `evals/routing-evals.json`。脚本检查的是 schema 合法、id 唯一、prompt 不重复、负例给了 `route_to`、边界用例写了两可理由，以及 `SKILL.md` 的 description 是否写了负触发范围。

**它不验证模型是否真的按预期触发**——那要在干净会话里逐条发 prompt 比对，用 `--emit-prompts` 导出清单人工过。改动 description 之后必跑，负例是触发边界的唯一约束。

## 五、技能包内部契约自检

前面四节管的是技能产出的文档。这一节管技能包自己。

```bash
python3 scripts/self_check.py                 # 全部二十项
python3 scripts/self_check.py --only S03,S07  # 只跑指定项
python3 scripts/self_check.py --list          # 列出检查项
python3 scripts/self_check.py --format json
```

退出码：0 通过，1 契约错误，2 用法错误。

存在的理由：模板、脚手架、校验器三层靠字符串约定耦合，任一层单独改都会**静默失效**——渲染出没替换的 `{{FOO}}`、校验器解析不到表而误判通过、schema 与脚本常量各说各话。这类错误不报错，只会安静地放行，所以必须有机器检查。其中 S05 最关键：改了模板的章节标题或表头而没同步校验器，表现是「检查通过」。

| 编号 | 检查项 | 咬住的漂移 |
|------|--------|------------|
| S01 | SKILL.md frontmatter 与版本一致性 | version / EXAMPLE_STATE.skill_version / CHANGELOG 三处版本号脱节；版本序列跳号或走错层级（该记补丁号却升了次版本号）；最新版本没排在 CHANGELOG 最前；description 超长或缺负触发范围 |
| S02 | 访谈 schema 与脚本常量一致 | 门禁项、状态字段、status 取值在 schema 与 `validate_interview.py` 常量之间漂移；`--print-example` 的样例自身不合法 |
| S03 | 模板占位符与脚手架提供的键一一对应 | 模板新增 `{{FOO}}` 而脚本不提供，产物里原样残留；模板未被加载 |
| S04 | 关系类型词表在两个脚本中一致 | 两份 `RELATION_MIRROR` 不一致；镜像不对合；文档第 5 节与 `VALID_RELATIONS` 脱节 |
| S05 | 文档解析约定与模板实际标题／表头对得上 | 改了模板标题或表头，校验器解析不到内容而误判通过 |
| S06 | 禁用词表两栏与脚本常量一致 | `writing-style.md` 2.1 栏与 `BANNED_WORDS` 漂移；2.2 栏的短词被误加进脚本 |
| S07 | 自举与真实数据冒烟：空白骨架零 ERROR 且真实数据不崩 | 模板与脚本的契约已断；产物残留占位符；`--strict` 卡不住空白骨架；`_load_registry` 的真实数据路径（双语标准名、豁免搭配、配置矛盾）有 bug--空白骨架的占位行跳过这些分支，出厂才漏网 |
| S08 | 引用的技能内文件真实存在 | 文档提到包内不存在的文件；引用了外部站点 |
| S09 | 技能包自身遵守写作规范 | 模板命中禁用词（会让每份基于它生成的文档都触发 C08）；模板用了 emoji |
| S10 | 检查项编号在脚本与文档中一致 | `CHECKS` 与本文档的检查项表脱节 |
| S11 | 模板固定文案不埋 C07 地雷 | 模板正文用了用户可能登记为禁用同义词的业务名词（订单、回退、校验…），导致每份产物都报 C07 而违规出自模板 |
| S12 | 模板版本契约与校验器一致 | 模板漏写「文档版本」行或变更记录缺版本列，C11 会把「模板没给」误报成「用户没填」；七份模板初始版本不一致 |
| S13 | 访谈链负例冒烟 | validate_transcript 的负例（两个问号、推荐缺理由、首问前无 evidence_read、门禁/阻塞/expansion 违规、final 早于 approval、resume 接续错/哈希不符）有任一咬不住 |
| S14 | 影响分析与复核销项冒烟 | 临时 git 仓库改一份模块文档，impact_analysis 未报出受影响的综述/跟踪矩阵/关联模块；全量销项后门禁未放行或缺销项节；异常销项条目未被点名；销项清单在场时状态未回退未拦住 |
| S15 | 路由脚本冒烟 | run_routing_evals 默认用例未通过结构校验、--emit-prompts 导不出复核清单 |
| S16 | 人工复核清单脚本冒烟 | manual_review_checklist 在空白骨架上退出码非 0、输出缺节（独立清单与源码推导双查）、节数与 EXPECTED_HEADS 不等 |
| S17 | 文档状态词表在三处一致 | `decomposition-rules.md` 第 8 节、`VALID_DOC_STATUS`、脚手架副本三处漂移（两个方向都查）；初始态不在词表或被列进 `FROZEN_DOC_STATUS`；模板正文又抄一份取值列举 |
| S18 | 取值词表人读版与机器版一致 | 置信度（§6 ↔ `VALID_CONFIDENCE`）、依赖强度（§7 ↔ `VALID_STRENGTH`）、NFR 判定（templates ↔ `VALID_NFR_VERDICT`）、ID 前缀（§4 ↔ `ID_PREFIXES`）四处取值漂移。此前只有 S04 守关系类型、S17 守文档状态，这些无人守 |
| S19 | 聚合视图脚本冒烟 | build_view 在空白骨架上退出码非 0、输出缺模块标题或章节，或对不存在的模块没退 2 |
| S20 | 人工自查词表与 §2.2 一致 | MANUAL_WORDS（manual_review_checklist）与 writing-style §2.2 两份副本漂移 |

S07、S13、S14 会在临时目录跑一遍完整的脚手架展开与校验或 git 操作，比其余各项慢几秒。

## 六、CI 接入

模板在 `assets/ci/`：

- `github-actions-requirements-check.yml` → 放到 `.github/workflows/`。PR 触发全量校验与影响分析，报告以评论形式贴回 PR，存在未同步文档时阻断合并。
- `pre-commit-config.yaml` → 放到仓库根目录。提交时跑校验，推送时跑影响分析。

两份模板都需要改 `DOC_DIR`（文档目录）与 `REPLACE_WITH_SKILL_PATH`（技能包在你仓库中的路径）。GitHub Actions 模板会检查占位符是否已替换，没替换就直接失败——静默跳过校验比报错危险。

本技能不绑定任何托管平台。换 GitLab CI、Jenkins 或本地钩子时照搬命令即可，退出码语义一致。

## 七、脚本依赖的文档约定

校验脚本靠标题关键词和表头关键词定位内容，改动模板时保持下列约定，否则解析不到：

| 内容 | 定位依据 |
|------|----------|
| 综述 / 术语表 / 跟踪矩阵 / 版本计划 | 文件名分别含「综述」「术语表」「跟踪矩阵」「版本计划」 |
| 模块文档 | 文件名以 `MOD-NNNN` 开头 |
| 场景文档 | 文件名以 `UC-NNNN` 开头 |
| 决策记录 | 文件名以 `ADR-NNNN` 开头 |
| 版本快照 | 文件名含「版本快照」或「snapshot」 |
| 模块索引表 | 标题含「模块索引」，或表头同时含「模块」「状态」 |
| 全局 NFR 表 | 标题含「非功能」或「NFR」，或表头同时含「NFR」「阈值」 |
| 关系矩阵表 | 标题含「关系矩阵」，或表头同时含「关系类型」「置信度」 |
| 关系本地视图表 | 标题含「关系本地视图」 |
| NFR 适用性声明表 | 标题含「NFR 适用性」，或表头同时含「NFR」「结论」 |
| 业务规则清单表 | 标题含「业务规则」，或表头同时含「规则 ID」「规则描述」 |
| 数据需求表 | 标题含「数据需求」，或表头同时含「实体」「写主」 |
| 数据实体属性表 | 标题含「数据实体」，或表头同时含「实体」「写主模块」；术语表第 2 节，C13 交叉核对写主时用 |
| 术语表主表 | 表头含「标准名」或「术语」，同义词列名含「禁用同义词」，豁免列名含「豁免上下文」（模板预填，不可省略） |
| 文档状态行 | 元信息表（「项 \| 值」两列竖表）里项列**全等**于「状态」。用全等而非子串：「状态」两字太短，子串会命中流程表的「前置/后置状态」，把正文当成状态取值 |

代码块内的内容会被跳过，Mermaid 图中的示例 ID 不会触发误报。C14 例外：它专门解析 ```mermaid 块，查图内的真实 `MOD-NNNN` 是否登记（泛指的 `MOD-NNNN` 不匹配数字，不触发）。标题与表头的替代关键词（如「模块清单」「NFR适用性」「关系视图」等）见 `validate_requirements.py` 的 `TABLE_SPECS`。

**泛指某个 ID 时写 `MOD-NNNN`，不要写 `MOD-XXXX`**——`XXX` 在 C09 的占位符黑名单里，会被判为「残留占位符」报 ERROR。

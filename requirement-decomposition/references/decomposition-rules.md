# 拆分规则与标识规范

拆分阶段的判定依据。骨架轮（第 1 轮）和逐模块轮（第 3 轮）必读。

## 裁剪层级

本技能包产出的默认形态是**标准层（L2）**：综述 + 模块文档 + 场景切片 + 术语表 + 跟踪矩阵 + 版本计划 + 全套校验护栏。按项目规模与风险裁剪：

| 层级 | 适用 | 相对 L2 的增删 |
|------|------|----------------|
| L1 轻量 | 探索期、小工具、单人项目 | 减内容深度：关系矩阵置信度、NFR 强制声明、版本快照基线可留空；保留模块拆分、术语表、核心场景 |
| L2 标准 | 多数产品项目 | 默认全套 |
| L3 严格 | 受监管、高复杂、分布式系统 | 加：扩展产物（接口契约、风险登记册、权限矩阵、数据字典、威胁模型、状态机），模板见 references/optional-extensions.md |

裁剪的是内容深度与校验项数量，不是删产物文件——骨架照常展开（C01 必需文件不能删，删了报 ERROR），L1 的产物文件保留、内容可留空标 `[待确认]`，校验用 `--only` 跳过非必需项。底线任何层级都跑：C01 必需文件、C02 ID 引用、C03 链接。

## 1. 模块粒度：六项测试

功能模块的定义是**最小可独立验证单元**。候选模块必须同时通过下列六项，否则拆开或合并。

| # | 测试项 | 通过标准 | 不通过的信号 |
|---|--------|----------|--------------|
| 1 | 目标单一 | 一句话说清它负责什么，句中不含「和」「以及」「同时」 | 「负责订单创建和支付回调以及退款」 |
| 2 | 契约明确 | 能写出输入、输出、前置条件、后置条件、异常出口 | 输入写成「用户的各种操作」 |
| 3 | 可独立测试 | 能构造一组测试数据，不启动其他模块就验证它的产出 | 必须先跑完另外三个模块才能验 |
| 4 | 高内聚 | 内部所有规则都围绕同一份数据所有权 | 一半规则改 A 表，一半规则改 B 表，两者无关 |
| 5 | 低耦合 | 对外依赖 ≤ 3 个模块，且都能在关系矩阵里写清楚 | 依赖七八个模块，说不清顺序 |
| 6 | 场景规模 | 主要场景 1~3 个 | 罗列出 9 个场景，其中 4 个互不相干 |

场景数超过 3 个时，先看是否属于同一业务规则的变体。是变体则保留为备选流；不是则拆分。

## 2. 边界从哪来

按优先级依次尝试，用第一个能给出清晰边界的方法。

1. **业务子域（DDD）**：识别限界上下文，边界落在上下文之间。语言不通用的地方就是边界——同一个词在两侧含义不同（「订单」在履约域指发货单，在计费域指账单），说明这是两个模块。
2. **数据所有权**：谁负责某份数据的写入和一致性，谁就是这个模块。一份数据只能有一个写主，读方通过接口获取。两个候选模块争夺同一份数据的写权限时，合并或重新划线。
3. **业务规则聚合**：一组必须同时变更的规则归入同一模块。判断法：改需求 X 时要同时改哪几条规则，这些规则就在一起。
4. **角色与生命周期**：由不同角色在不同阶段触发、且中间存在明确状态跃迁的，可以拆。

## 3. 反面清单

| 错误拆法 | 症状 | 修正 |
|----------|------|------|
| 字段级拆分 | 「手机号校验模块」「邮箱校验模块」 | 合并为「注册信息校验」，字段差异写成业务规则表 |
| 大杂烩模块 | 「订单管理」「用户中心」「后台管理」 | 按子域拆：下单、改单、取消、履约状态同步 |
| 技术分层当模块 | 「接口层」「服务层」「数据层」 | 按业务能力重划，技术分层属于架构文档不属于需求拆分 |
| 公共/工具模块 | 「通用工具」「公共服务」「基础能力」 | 拆到具体归属方；确实跨模块共用的是**规则**，写进综述的全局跨模块规则 |
| CRUD 四连 | 「新增」「删除」「修改」「查询」各一个模块 | 合并为一个模块，四个操作是它的场景 |
| 页面即模块 | 按原型页面数量一一对应 | 一个页面可能触发多模块；页面写进 `UI-NNNN` 界面引用 |

**模块内出现强分支**（例如「个人用户走 A 流程、企业用户走 B 流程」，两条流程的业务规则重合度低于一半）：立即拆为子模块，对外接口保持不变，关系矩阵登记为组合关系。

## 4. ID 规范

| 前缀 | 用途 | 格式示例 |
|------|------|----------|
| `MOD` | 功能模块 | `MOD-0001`、`MOD-0007` |
| `NFR` | 全局非功能需求 | `NFR-0003` |
| `UC` | 端到端场景切片 | `UC-0002` |
| `REQ` | 模块内需求条目 | `MOD-0001-REQ-0004` |
| `TERM` | 术语 | `TERM-0011` |
| `UI` | 界面/原型引用 | `UI-0005` |
| `ADR` | 决策记录 | `ADR-0003` |
| `RULE` | 全局跨模块规则（综述第 8 节） | `RULE-0001` |
| `AC` | 验收标准，序号段与所属模块一致，子模块含字母后缀 | `AC-0003-0001`、`AC-0003-A-0001` |

规则：

- **序号四位起，从 `0001` 开始，不足四位在前面补 0**。全局唯一，**已分配的 ID 永不复用**。位数写少了（`MOD-01`）不会被当成 `MOD-0001`，C02 会报「序号不足四位」并给出正确写法。
- 超过 9999 时自然进位到五位，不必回头改已有 ID——正则按「四位起」匹配，`MOD-10000` 合法。
- 模块作废时状态改为「已废弃」并保留条目，不删除、不让后来的模块顶替它的号。
- 子模块用 `MOD-0003-A`、`MOD-0003-B`，不新占父级序号。
- 文档间引用一律写成 Markdown 链接：`[MOD-0001 订单创建](./modules/MOD-0001-订单创建.md)`。裸写 ID 不算引用，校验脚本会报缺链。

## 5. 关系类型词表

关系矩阵只允许使用下列十种类型，不自造词。

| 类型 | 判定标准 | 是否对称 |
|------|----------|----------|
| 依赖 | A 缺少 B 的产出就无法完成 | 否（B 侧登记为「被依赖」） |
| 关联 | 双方共享业务语义，但都能独立完成 | 是 |
| 组合 | A 由若干子模块构成，子模块不独立对外 | 否（子模块侧登记「隶属」） |
| 顺序 | 业务上 A 必须先于 B 发生，但 B 不消费 A 的产出 | 否（B 侧登记「后置于」） |
| 互斥 | 同一业务实体上 A 与 B 不能同时生效 | 是 |
| 约束 | A 的规则限定了 B 的取值范围或执行条件 | 否（B 侧登记「受约束于」） |
| 数据共享 | 读写同一份数据实体，需注明写主 | 是 |
| 事件触发 | A 发出事件，B 订阅后异步执行 | 否（B 侧登记「被触发」） |
| 回退 | A 失败时由 B 承接补偿或降级 | 否（B 侧登记「补偿对象」） |
| 泛化 | A 是通用抽象，B 是遵循同一接口的具体变体 | 否（B 侧登记「特化」） |

**对称性要求**：任一关系必须在双方文档的「关系本地视图」中各出现一次，方向互补。校验脚本检查这一点。

**依赖与顺序不可成环**：这两类关系有严格先后语义，A 依赖 B 且 B 又依赖 A，意味着谁都无法先启动。校验脚本对依赖/顺序关系检测环路并报 ERROR，镜像写法（「被依赖」「后置于」）会归一化后一并计入建图--写成镜像词绕不过环检。发现环就打破它：改为数据共享，或把其中一条降级为弱依赖并写明降级策略。

## 6. 置信度

| 取值 | 含义 | 升级条件 |
|------|------|----------|
| 已证实 | 有需求原文、接口契约或干系人书面确认支撑 | —— |
| 推测 | 依据行业常识或上下文推断，未经确认 | 里程碑评审时逐条过，确认后升级 |
| 待定 | 已识别出关系但方向或强度未知 | 补充调研后升级为推测或已证实 |

第 1 轮生成的关系默认全部标「推测」。**不要为了让文档看起来完整就写「已证实」**。

标「推测」「待定」的关系，必须在关系描述里写明判定依据（谁判的、依据什么，如「模型推断，待评审」「源自 PRD 第 3.2 节」）。没有依据的推测无法被评审升级，也无法被证伪。「已证实」必须能指认依据（需求原文 / 接口契约 / 干系人书面确认），指认不出就降级为「推测」。

## 7. 依赖强度与降级

每条依赖关系都要标强弱：

- **强依赖**：被依赖方不可用时，本模块整体不可用。必须写明失败表现（报错文案、状态码、是否可重试）。
- **弱依赖**：被依赖方不可用时，本模块降级运行。必须写明降级策略——降级后哪些能力保留、哪些关闭、数据如何补偿、恢复后如何对账。

只标强弱不写策略的，视为未完成。

## 8. 文档状态

文档状态回答的是「这一版能不能信」，文档版本回答「改到第几版」。两个问题都要答，缺一个读者就无从判断手里这份能不能拿去实现。

本节是状态词表的人读版权威源，机器版是 `validate_requirements.py` 的 `VALID_DOC_STATUS`，两者由 `self_check.py --only S17` 核对逐字一致。

### 8.1 取值

按**读者能否行动**切分，不按加工阶段切分。

| 状态 | 对读者的含义 | 进入条件 |
|------|--------------|----------|
| 草稿 | 别拿去实现，随时会变 | 骨架展开时的默认值；或从已评审／已冻结解冻修订 |
| 已评审 | 结论可信，可以据此设计与排期 | 人工评审通过，且 `--strict` 已过 |
| 已冻结 | 可以实现，改它要走变更流程 | **当前这一版**已被写入某次版本快照基线 |
| 已废弃 | 别看了，ID 保留不复用 | 显式废止 |

ADR 用的是另一套词表（提议 / 已采纳 / 已废弃 / 被取代），管的是一个决策的处置结果，不是文档修订的生命周期。两套不通用，「被取代」在文档状态里没有对应语义。

### 8.2 转移

```
                  评审通过           进入基线
        草稿 ──────────────> 已评审 ──────────> 已冻结
         ^                     │                  │
         └───────── 解冻修订 ──┴──────────────────┘

    任意状态 ──显式废止──> 已废弃（终态，ID 不复用）
```

**已冻结不得直接回已评审。** 冻结的文档要改，必然经历「正文被改动」这个事实，那就得先回草稿、重新走评审。允许直连的话，已评审会退化成一个可以随手贴上的标签——与访谈协议禁止 `interviewing` 直跳 `awaiting-approval` 同源：跳过中间态等于跳过它的进入条件。

### 8.3 状态跃迁是一个原子动作

一次跃迁同时改四处，缺一处就不算跃迁完成：

| # | 改什么 | 谁检查 |
|---|--------|--------|
| 1 | 模块文档头部的「状态」行 | C15 |
| 2 | 综述模块索引表的状态列 | C15 |
| 3 | 元信息表的「文档版本」进位 | C11 |
| 4 | 变更记录新增一行，版本与 3 相等 | C11 |

**权威源是模块文档头部**，综述索引表是视图。改模块的人顺手改状态，模块文档单独发出去也自带状态；两处不一致时 C15 报 ERROR 并给出两个行号。

进位幅度仍按「读者是否需要重读」判，状态跃迁不额外规定幅度。两个例外：评审通过而正文一字未改时进修订号（变更记录行必须配一个版本号）；打基线转已冻结时不进位（快照记的就是当前这一版，进位会让快照版本与被快照的版本对不上）。

### 8.4 已冻结绑的是版本，不是文件

「已冻结」说的是「基线里那一版内容不再改动」，不是「这个文件曾经进过基线」。所以 C15 比对的是版本号：已冻结文档的当前版本必须能在版本快照的基线记录里找到。

对不上意味着进基线之后正文又改过——冻结的是基线里那一版，不是现在这一版。两条出路：退回「草稿」重走评审，或者当前这一版确已评审通过，补打一次 `--snapshot`。

只比文件名的话，「改正文、升版本、状态不退」这一手完全看不出来：文件名还在基线里，检查照过。

### 8.5 版本快照文档不参与

`04-版本快照.md` 每次打基线都被追加内容，正文必然改动。给它加状态行会让它永远处于「刚被改过」的状态。它记录历史，本身不参与生命周期——C15 与 `impact_analysis.py` 都显式豁免它。

## 9. 硬性禁止

1. **禁止隐式假设**。凡是「这里应该会有个xx服务提供」的地方，都要显式写出依赖模块并在关系矩阵登记。写不出来就标 `[待确认]` 并列入待办，不许含糊带过。
2. **禁止在模块文档内重复定义全局 NFR**。模块只声明适用性，指标数值一律引用 `NFR-NNNN`。
3. **禁止非单一职责的公共模块**。
4. **禁止同义替换**。术语表里叫「履约单」，全文就只能是「履约单」，不许写成「发货单」「配送单」「订单」。标准名支持中英双语并列（如 `Order / 订单`），各形式等价、按当前文档语境任选其一使用；只有禁用同义词列登记的说法才需替换。
5. **新概念必须标记**。生成过程中出现术语表没有的名词，标 `[新增术语提案]` 并在该轮结束时汇总提交，不许直接当既有术语使用。

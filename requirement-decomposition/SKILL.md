# 需求拆解与需求文档网络生成

把零散的原始需求（口述、会议纪要、旧文档、竞品分析）转成一套互相引用、可追溯、可验证的需求文档，而不是一份越写越长、没人读得完的大文档。

核心结构是总分：一份**综述**承担全局索引、非功能需求、术语、关系矩阵；每个**功能模块**一份独立文档，只写自己的事，通过 ID 引用回综述；若干**端到端场景切片**横穿多个模块，反向验证拆分是否合理。

## 适用与不适用

适用：需求量大到单文档装不下、多人协作分工写需求、需要做需求追溯与影响分析、需求会反复变更。

不适用：只有三五条需求的小改动，用一份文档更省事；纯技术方案设计（那是架构文档，不是需求文档）。

## 工作流

六轮推进。**每轮结束都跑一次校验**，不要攒到最后。

### 第 1 轮 · 骨架

只产出结构，不写细节。这一轮的错会被放大到几十个文档里，慢一点值得。

1. 通读原始材料，按 `references/decomposition-rules.md` 第 1~2 节切分模块。每个候选模块过一遍六项测试，不通过就拆或并。
2. 输出四份清单：
   - **模块清单**：`MOD-NNNN` + 名称 + 一句话目标
   - **关系草稿**：源、目标、关系类型、依赖强度，置信度**一律先填「推测」**
   - **NFR 候选**：`NFR-NNNN` + 类别 + 指标，写不出阈值的标 `[待确认]`
   - **术语候选**与**核心场景候选**（3~5 条旅程）
3. 把清单写成骨架 JSON（结构见 `scripts/scaffold_docs.py --print-schema`）。

**不要在这一轮写任何流程、规则、字段。**

骨架写完先预演展开验证（ID 合法、status 全为草稿），展开成功即可删临时目录：

```bash
python3 scripts/scaffold_docs.py skeleton.json -o /tmp/骨架预演 && rm -rf /tmp/骨架预演
```

### 第 2 轮 · 访谈确认

这一轮阻塞。骨架的错会被脚手架复制到几十份文档里，改一处边界要返工整批模块文档与场景切片——展开之前多问五个问题，比展开之后重写便宜。

完整协议见 `references/interview-protocol.md`，进入本轮前读它。要点：

1. **证据优先**。第一个问题之前先通读原始材料，每份记路径、SHA-256、一句话结论。材料能回答的不许再问用户。
2. **一轮一个决策**，必带推荐答案与选它的理由。不许把第二个问题藏进括号或「另外」。
3. **按风险排序**：模块边界 → 数据写主 → 强弱依赖 → NFR 阈值 → 范围外 → 场景取舍。
4. **八项门禁全真才出骨架**。阻塞项（会改变边界、写主、依赖强度的）不满足就继续问；非阻塞项标 `[待确认: 描述]` 登记进未决清单放行。
5. **批准之前不展开目录**、不写模块正文、不写实现代码。沉默不算批准。

状态落 `interview-state.json`（结构见 `schemas/interview-state.schema.json`），中断后从唯一的 `next_question_id` 接续，不重问已定项。每轮校验：

```bash
python3 scripts/validate_interview.py --state interview-state.json --transcript transcript.json
```

用户明确批准后才展开：

```bash
python3 scripts/scaffold_docs.py skeleton.json -o ./需求文档
python3 scripts/validate_requirements.py ./需求文档 --only C01,C05
```

脚手架会自动把每个模块文档的 NFR 适用性声明表按全局 NFR 逐条铺好行，这是最容易漏的地方。

**批准授权的是骨架，不是后面五轮的内容。** 第 3 轮起正常推进，不再逐条阻塞。

### 第 3 轮 · 逐模块生成

一次只处理一个模块。喂给生成过程的上下文**只有三样**：骨架摘要（模块索引 + 关系矩阵 + 术语表 + NFR 表）、模板、该模块相关的原始需求片段。不要把其他模块的成品文档带进来——那是同义替换和职责串味的主要来源。

模块数超过 6 个时，用 Agent 工具并行分发，每个子任务只负责一个模块，任务提示里附上骨架摘要和该模块的需求片段。

填写标准见 `references/document-templates.md`「功能模块文档」一节。三条硬性要求：

- NFR 适用性声明逐条应答，「不涉及」不算理由。
- 术语只用术语表标准名，冒出新名词就标 `[新增术语提案]`，不许自行采用。
- 关系本地视图从综述矩阵**摘录**，不重写不改写。

每完成一个模块：

```bash
python3 scripts/validate_requirements.py ./需求文档 --only C02,C03,C04,C07
```

**C07 必须在这一轮逐模块清掉，不能留到定稿。** 它是唯一随文档量线性累积的检查项，且每条告警都要人读上下文才能决定怎么处理（换标准名 / 在术语表登记豁免上下文 / 加行内 `<!-- term-ok: 词 -->`）。攒到第 6 轮就是几十条一起判，逐模块跑则每次只有三五条，写的时候上下文还在脑子里。

处理 C07 告警时按这个顺序判，不要逐条硬想：

1. 该说法确实指术语表那个概念 → 换成标准名的相应形式（标准名可中英双语并列，按当前文档语境选），不加豁免。
2. 同形异义且这个搭配会反复出现（「失败回退加载」里的「回退」）→ 进术语表「豁免上下文」列，全库一次生效。
3. 同形异义但只此一处 → 该行加 `<!-- term-ok: 词 -->`。写在表格行里时多个词用顿号分隔，注释里的 `|` 会被当成列分隔符切错列（C10 会拦）。
4. 一轮下来某个词全是误报 → 说明它不该在禁用同义词列里，回术语表删掉，比逐条豁免省事。

### 第 4 轮 · 全局审查

全局审查分三层，不要把自查权全交给生成模型：

1. **脚本护栏**：跑 `validate_requirements.py`，管结构硬错误。
2. **独立语义审查**：派一个未参与生成的子任务，只看验收标准与改动 diff，审查语义一致性——同一规则是否多口径、关系描述与正文是否一回事、概念是否误用。它不该继承生成过程的叙事。
3. **人类抽查**（建议性）：高风险模块值得提前让人过一眼（见 `manual_review_checklist.py` 列出的复核项）。正式的内容背书统一在第 6 轮里程碑评审，本轮的抽查不触发任何状态转移。

```bash
python3 scripts/validate_requirements.py ./需求文档
```

脚本管得住的：ID 悬空、链接断裂、NFR 漏项、关系不对称与依赖/顺序成环、矩阵缺行、术语串味、写作禁用词、模块体量异常（C12）、数据写主冲突（C13）、Mermaid 图内悬空模块（C14）、文档状态取值与双处一致（C15）、终态文档引用完整性（C16）。

脚本管不住的，人工过一遍：

- 前置条件能否被上游模块的后置条件满足，接不上就是拆分有洞。
- 关系描述与模块正文说的是不是一回事。
- 过程中挡回去的技术选型问题是否都进了综述第 9 节「移交事项」，还是只在对话里说过就散了。

机器报信号、人定夺的两类：C12 报模块体量异常（合并还是拆子模块），C13 报同一数据有多个写主（冲突还是异形同义）--机器只指出位置，判断仍靠人。

上述复核项已固化成一条命令，按当前文档库列出具体待查条目，不再靠人记得该查什么：

```bash
python3 scripts/manual_review_checklist.py ./需求文档
```

**模块文档进入里程碑评审的完成定义（DoD）**：ID 已分配且唯一；NFR 适用性声明逐条无留白；至少 1 条基本流与 1 条异常流；至少被 1 个场景引用；术语全部来自术语表；跟踪矩阵行已建立。这些大多有对应校验项（C02/C04/C06/C07），`--strict` 清零即满足大半——DoD 是把它们聚成一道评审门槛，不是新增机制。

**本轮不做状态转移，全库保持「草稿」。** 草稿是生成期的诚实中间态；内容背书统一在第 6 轮里程碑评审一次完成。提前转「已评审」只会让第 5 轮的返工（场景走查不通回改模块）背上先退状态再重评审的成本。

**本轮暴露的结构性分歧补写决策记录**。第 2 轮访谈里争过的决策同样在此补齐——访谈的决策记录只留了结论，ADR 要把被否决的方案和理由一并写下。

判据见 `references/document-templates.md` 第六节：有过真实争议、会约束多个模块、属于原则的例外、前提可能变化——满足任一条就建一份 `decisions/ADR-NNNN-标题.md`。没争议的事实不写 ADR。

### 第 5 轮 · 场景编写

模块稳定后再写场景，否则返工。每条旅程一份文档，引用模块文档里**确切的步骤编号**。

场景跑不通说明拆分有问题——回到第 4 轮改模块，不要在场景里打补丁绕过去。把发现记进场景文档的「拆分验证结论」。

场景类型按覆盖清单核对，不是只写 happy path：正常 / 备选 / 异常 / 边缘（并发冲突、极端输入）必盖；性能 / 安全 / 灾难恢复 / 迁移 / 多端 / 弱网 / 可访问性 / 国际化按项目裁剪，声明「本期不涉及 + 理由」，不许静默略过。

场景写完跑校验（链接、ID 引用、Mermaid 图内模块）：

```bash
python3 scripts/validate_requirements.py ./需求文档 --only C02,C03,C14
```

场景文档的内容背书同样后置到第 6 轮里程碑评审，本轮结束不转状态。

### 第 6 轮 · 版本规划与里程碑评审

填版本计划：各版本包含的模块与需求、前置版本、发布条件。

重点是跨版本降级策略：模块 A 上线而它依赖的 B 排在下个版本时，A 在等待期怎么跑、数据怎么补、B 上线后怎么对账。强依赖不允许跨版本拆开上线。

然后是**里程碑评审**——全流程两个人工触点中的第二个（第一个是第 2 轮骨架批准）。它是事件不是过程：第 3~5 轮全库停在「草稿」是诚实的中间态，全部内容背书集中在这一次完成。事件按四步推进，**收敛于全量通过，不许结束于打回**。

**① 机器备料**（零人工判断）：

```bash
python3 scripts/validate_requirements.py ./需求文档 --strict   # ERROR 与 WARN 均清零
python3 scripts/manual_review_checklist.py ./需求文档          # 机器管不到的复核项
```

组装评审包：复核清单 + 全库状态与版本汇总 + 本轮 diff 摘要（`impact_analysis.py --format markdown`）。文档量大时按主题用 `build_view.py` 出聚合视图，评审人不用逐份翻文件。

**② 评审**（人）：整体说「通过」，或逐份打回并**写明打回理由**。理由不可执行（「不行，重写」之类）时不许猜着修——先澄清，再动手。

**③ 打回修复回路**（agent 执行，草稿态零状态成本）：逐份修复并附修复说明，然后判定**对外契约面**（步骤编号 / 关系边 / 数据写主 / 数据实体的字段口径 / 前置后置条件 / NFR 应答 / 术语，清单的唯一来源是 `references/decomposition-rules.md`）：

- **契约面未动**：邻接文档的批准保持有效，修复后全量校验重跑即可。
- **契约面动了**：受影响邻接（按关系矩阵反查：1 跳邻接 + 综述/跟踪矩阵/相关场景/点名 ADR）的**批准作废**，并入增量评审集。对一份文档的「通过」背书的是它的内容加上它依赖的内容——前提变了，批准作废。「只改被打回那一份」在这种情形下不能通过。

增量复审只看修复文档 + 失效邻接 + 影响面论证，已通过的部分不重读。失效范围机器算：批准集记录批准时的版本号，当前版本变了即失效，再按关系矩阵传播——与维护期的「受影响但未同步」是同一张图、同一套传播语义。**同一文档连续两轮被打回即升级**：人直接介入修改，或回第 1~2 轮重估该模块的骨架——文字层修不好的问题多半在边界层。

**④ 机器扫尾与定稿宣告**（收敛之后）：

```bash
# 一、转「已评审」：文档头部与索引表两处一起改，进修订号并加变更记录行（评审留痕）
# 二、打基线。非「已评审」的文档会在 stderr 列出，--strict 时退出 1
python3 scripts/validate_requirements.py ./需求文档 --snapshot 2026-08-16 --strict \
  >> ./需求文档/04-版本快照.md
# 三、把进了基线的文档转「已冻结」，再验一次——C15 会列出进了基线却没转的
python3 scripts/validate_requirements.py ./需求文档 --only C15
```

顺序不能换：`--strict` 没过就打基线，记的是一份带着未决项的内容；状态没转「已冻结」，C15 会报「进了基线却没转」的反向情形。脚本不回写文档，状态改动在人说「通过」之后执行。

批准与打回连同理由登记进 `04-版本快照.md` 的「评审记录」节。定稿宣告包含三样：全库状态汇总（**终点是全库终稿，零草稿残留**）、维护期入口（见「变更维护」节）、本次里程碑待办（置信度集中升级、销项登记、耦合审计）。

**「已冻结」绑的是版本不是文件**。C15 拿当前版本去基线记录里找，找不到就报——进基线之后又改正文、升了版本却不退状态，冻结的已经不是现在这一版了。这时要么退回「草稿」重走评审，要么当前版本确已评审通过就补打一次 `--snapshot`。

## 版本与修订

### 三种「版本」先分清再统一

同一批文档里出现 V1、V1.0、v0.1、不写四种写法，根源不是笔误，是三个语义共用了一个词。**先分离语义，再统一格式**——否则统一的是错的东西。

| 语义 | 字段 | 谁定格式 |
|------|------|----------|
| 文档修订：这份 Markdown 改到第几版 | `文档版本` | 本技能，三段号 `V1.0.0` |
| 产品发布：需求排进哪个迭代上线 | `目标版本` | 产品，本技能不管 |
| 模块引入：模块从哪个产品版本开始存在 | `引入版本` | 引用产品版本，不独立进位 |

版本回答「改到第几版」，状态回答「这一版能不能信」。两个问题都要答——拿到一份 `V1.3.0` 而不知道它评审过没有，这个号就用不上。状态词表与转移条件见 `references/decomposition-rules.md` 第 8 节，C15 校验。

把「引入版本」也改成三段号是错的：它记的是模块从哪个产品版本开始存在，强行三段化反而污染产品版本语义。

### 进位判据是「读者是否需要重读」

不是改了多少字。文档的消费者是评审人和实现方，他们只关心「我上次读的还算不算数」。

主版本号——需求范围或边界变了，需重读全文；次版本号——内容新增或结论变化，局部重读；修订号——措辞与笔误，结论不变。一次只进一位。

改正文必须同步加变更记录行，头部版本与变更记录最新一条必须相等。骨架展开时全库 `V1.0.0`。

### 改动前阶段内容时保留痕迹

需求文档的读者跨版本引用：第 5 轮的场景引用第 3 轮模块文档的确切步骤编号。第 6 轮直接删掉那一步，引用就悬空了——而 ID 与链接检查看不出「步骤 4 曾经存在」。

按改动性质选形式：所有改动都记变更记录行；结论变了且旧结论已被引用，加行内 `<!-- rev: 版本 原为… -->`；整节作废则保留原文加删除线并标 `[版本 废止: 理由]`，不直接删。

判据表与写法见 `references/quality-gates.md`，校验由 C11 承担。评审定版时用 `--snapshot` 生成版本快照锁定基线。

**改已评审或已冻结的文档，先把状态退回「草稿」。** 状态与版本一起动：退状态、进版本号、加变更记录行。`impact_analysis.py` 会揪出「正文改了但状态没退」的文档——正向路径靠人记得走，退回这一步没人想主动做，只能靠机器盯。不退的话，跑上三个月全库都是「已冻结」而没有一份真的冻结着。

八个脚本只依赖 Python 标准库，不访问网络、不绑定托管平台：`scaffold_docs.py` 展开目录，`validate_requirements.py` 十六项检查，`impact_analysis.py` 变更影响分析，`validate_interview.py` 访谈契约校验，`run_routing_evals.py` 触发用例结构校验，`manual_review_checklist.py` 列出脚本管不到、需人工过的复核项，`build_view.py` 按视图配方拼装聚合视图，`self_check.py` 技能包自身的内部契约自检。

其中六个管产出的文档（`manual_review_checklist.py` 与 `build_view.py` 复用同一份文档索引，前者列出机器管不到的语义复核项，后者按视图配方拼装聚合视图）；`run_routing_evals.py` 管技能包自身的触发用例；`self_check.py` 管这个技能包自己的内部契约——改本包任何文件后跑它。

## 变更维护

首个里程碑之后进入维护期：变更在草稿态自由迭代（改已评审或已冻结的文档先把状态退回「草稿」），攒到下一个里程碑评审统一复审、重打基线——里程碑事件的形态与收敛条件与第 6 轮相同，终点同样是全冻结。

需求变更后不要只改一处：

```bash
python3 scripts/impact_analysis.py --dir ./需求文档 --base origin/main --fail-on-unsynced
python3 scripts/impact_analysis.py --dir ./需求文档 --changed-files 清单.txt   # 不在 git 仓库时
```

脚本按关系矩阵推导受影响文档并检查是否同步更新。模块内容变了而综述、跟踪矩阵、相关场景没动，一律列为未同步。

邻接传播是粗粒度的：全部邻接模块都会进「受影响」清单。逐份复核后确认无需改动的，把清单喂给 `--cleared` 让门禁如实通过，不要靠空转版本号销项——空转进位腐蚀 C11 的进位判据。销项豁免不了「状态未回退」，也不跨变更集粘连；里程碑评审时把本轮销项登记进 `04-版本快照.md` 的「变更复核登记」节。

脚本拦得住「没同步」，拦不住「不知道该改」。模块的结构性修改（改变关系、数据共享、前置/后置条件）除了同步受影响文档，还要在变更记录写明影响说明，并通知依赖方——即在关系矩阵里登记为「被依赖」「被触发」「数据共享」对方的模块负责人。

里程碑评审时一并做三件事：置信度集中升级（把所有「推测」过一遍，确认的改「已证实」，仍不确定的保持原状并记录阻塞原因）；销项登记（上一条）；耦合审计（找出文档里没声明但实际存在的依赖，补进矩阵，复核项见 `manual_review_checklist.py`）。

## 硬性约束

1. **不写空洞话**。删掉后读者理解无损失的句子不要写。写作规范见 `references/writing-style.md`，校验脚本 C08 会扫。
2. **不编造细节**。字段名、阈值、接口、状态取值，凡是材料里没有的，标 `[待确认]`，不要填一个看起来合理的值。编造的代价远大于留空。
3. **不作同义替换**。术语表定死的名词，全网络只能用那一个说法。
4. **不留隐式假设**。「应该会有个服务提供这个」必须写成显式依赖并登记进关系矩阵。
5. **不在模块内复述全局 NFR 的指标**。只声明适用性，数值引用 `NFR-NNNN`。
6. **不建「公共模块」「工具模块」**。真正跨模块共用的是规则，写进综述第 8 节。
7. **ID 永不复用**。模块作废改状态保留条目，不让新模块顶替旧号。

## 不做什么

| 这类请求 | 不用本技能，改用 |
|----------|------------------|
| 「给用户表加个手机号校验」——三五条需求的小改动 | 一份文档写完更省事，拆成文档网络是净亏 |
| 「设计一下技术架构、数据库选型怎么做」 | 架构文档。本技能只写需求，不写技术方案 |
| 「写一份社区团购小程序的 PRD」——单份 PRD 创作 | 需求量大到单文档装不下时才回来拆网络 |
| 「调研在线教育赛道竞品格局，要引用来源」 | 多源引用的市场调研，拿到结论后再写进需求 |
| 「我们次留只有 20%，怎么提升」 | 产品策略与增长咨询 |
| 「按这份文档把接口实现出来」 | 需求文档交付即止，实现是另一个任务 |

边界情况：功能设计归本技能，深度技术选型不归——两者混在一起时，本技能主导需求部分，选型部分写进综述第 9 节「移交事项」。移交要落成产物，只在对话里说过的移交，交付之后没人记得。

## 已知陷阱

| 陷阱 | 表现 | 应对 |
|------|------|------|
| 骨架轮写细节 | 第 1 轮就开始写流程、字段、业务规则 | 第 1 轮只出四份清单；细节留到第 3 轮 |
| 问卷式开局 | 第 2 轮一次抛出十个问题让用户填 | 一轮一个决策，带推荐答案，用户可直接说「就按你说的」 |
| 材料里有却去问用户 | 接口契约写着的字段仍然发问 | 提问前先做证据登记，`evidence` 为空不许提问 |
| 跨模块串味 | 第 3 轮把其他模块成品文档带进上下文，导致同义替换 | 只喂骨架摘要 + 模板 + 该模块的原始需求片段 |
| 场景打补丁 | 场景跑不通，在场景文档里绕过去 | 回第 4 轮改模块拆分，把发现记进「拆分验证结论」 |
| 置信度虚高 | 为了让文档显得完整，把推测标成「已证实」 | 第 1 轮一律「推测」，里程碑评审才集中升级 |
| 编造填空 | 材料里没有的阈值填一个看起来合理的值 | 标 `[待确认]`。留空会被追问，编造会被当成事实实现 |
| 弱依赖不写策略 | 只标「弱依赖」，降级行为空着 | C05 会报错；降级后保留什么、关闭什么、怎么对账都要写 |

## 自查

每轮结束跑对应的校验命令（见各轮），定稿前这两条必须全过：

```bash
python3 scripts/validate_requirements.py ./需求文档 --strict   # ERROR 与 WARN 均清零
python3 scripts/impact_analysis.py --dir ./需求文档 --base origin/main --fail-on-unsynced
# 复核确认无需改动的受影响文档，加 --cleared 清单.txt 销项，不空转版本号
```

改动本技能包自身（模板、脚本、references）之后，另跑这两条：

```bash
python3 scripts/self_check.py            # 内部契约二十项，模板/脚手架/校验器三层的一致性
python3 scripts/run_routing_evals.py     # 改过 description 才需要
```

脚本管不住、必须人工过的三条：前置条件能否被上游模块的后置条件满足；关系描述与模块正文是否一回事；过程中挡回的技术选型问题是否都进了综述第 9 节「移交事项」。C12 报的体量异常与 C13 报的写主冲突由人定夺合并/拆分或异形确认；自然语言禁用词与路由触发也靠人过（见 `manual_review_checklist.py`）。
